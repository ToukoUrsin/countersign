## Background
`/home/ubuntu/junction/linearcodereview` is "Countersign" (hackathon project, Junction 2026, challenge "Earned Trust in AI Code"): an AI review pipeline turns a GitHub pull request written by a coding agent into a dossier (`data/dossiers/<slug>/dossier.json`, type in `shared/dossier.ts`), reproduces its findings as failing tests in a sandbox, and routes to a named human only what no run covers; a named human then countersigns (`server/index.ts`, gate in `shared/gate.ts`). Read `docs/CONCEPT.md`, `pipeline/review.ts`, `pipeline/lib/{ctx,agent,gh,sandbox}.ts`, `pipeline/stages/{intake,verify,route,publish}.ts`, and in `server/index.ts` the functions `startReview`, the webhook, the sign-off and `/api/dossiers/:slug/github`.

What is missing, and what a critic says would win the challenge: today a finding ends at the human. The winning story is a closed loop a judge can retell: **"It found a real bug with a failing test. The author agent pushed a fix. The old review was void, because evidence and signature are bound to one commit. The re-run proved the fix: the same test now passes. The merge stayed blocked on GitHub until a person signed."**

Sample to use: pull request #1 of the private repository `ToukoUrsin/junction26-messagepack-csharp` (our own copy of the challenge's sample; branch `ju26-issue-2283`, requirement REQ-2283). Its current dossier (`data/dossiers/toukoursin__junction26-messagepack-csharp__1/dossier.json`) has finding FN1 (major, reproduced: evidence E14 is a failing test Countersign wrote and ran), FN2 and FN3 (minor, reproduced), two decisions the AI refuses to make.

## What to build
1. **Rounds in the dossier.** Before a new review of the same pull request overwrites `dossier.json`, archive the old one next to it (`dossier.<sha7>.json`) and carry a compact history into the new dossier: `rounds: [{ headSha, at, verdict, findings: [{ id, title, severity, strength, reproTest? }], signoff?: { signer, decision, at }, fixRequest?: {...} }]` (additive type in `shared/dossier.ts`; the web UI and other readers must keep working when it is absent).
2. **Re-proof of earlier findings on the new head.** A new stage (or a step in `verify`) that takes every finding of the previous round that had a reproduction test (evidence kind `repro`: find where the test's source and run command are kept) and runs that same test, unchanged, on the new head in the sandbox: it failed on the old head; if it passes now the finding is `fixed` with new executed evidence ("FN1 of round 1: its failing test passes on <sha7>"), if it still fails it is `still-fails` and stays a finding of this round, if it no longer compiles or applies say `could-not-rerun` and why. Record this as `reproof: [{ fromRound, findingId, title, status, evidenceId }]`. The new round's own review runs as always and may find new things; that is a real outcome, report it.
3. **The fix request.** After a review is published, when the dossier has reproduced findings, Countersign writes the author agent a fix request: a comment on the pull request (posted the same way and by the same account as the existing dossier comment; look at `publish.ts`) that lists each reproduced finding with the failing test's code and how to run it, says what is NOT asked (the open decisions stay with the human; reasoned findings without a failing test are listed as context, not as orders), and carries the same content as a JSON block in an HTML comment so an agent can parse it. Policy switch `fixRequests: auto | off` in the policy file (default off; set `auto` in `policy/messagepack.countersign.yml`), at most 2 rounds per pull request, recorded in the ledger (`data/ledger.jsonl`, see how other events are appended) and in `rounds[].fixRequest`. A failing test is evidence, not an opinion, so this step needs no human; anything that is a judgment waits for the human.
4. **The author agent** (`work/author-agent/run.sh <PR url>`): it plays the coding agent that wrote the pull request. It clones the pull request's branch into a scratch directory under `/bulk2/runs/linearcodereview/author-agent/`, reads the newest fix request from the pull request's comments, and runs Claude Code headless on it (`claude -p ...` through the seat pool exactly as the pipeline's `runAgent` does it, see `pipeline/lib/agent.ts`; `hsec exec --only CLIPROXY_API_KEY -- bash -lc 'export ANTHROPIC_BASE_URL=http://127.0.0.1:8317; export ANTHROPIC_API_KEY="$CLIPROXY_API_KEY"; ...'`; never a paid API key, never print a secret) with the instruction: make the failing tests pass with the smallest correct change, add them to the test suite, do not resolve the open decisions, do not weaken or delete existing tests, and say in the commit message what you changed and what you left alone. It must not be shown Countersign's internals, the dossier, or this brief: only what a real author agent would see (the repository and the fix-request comment). It commits as the agent (same author identity as the existing commits on that branch) and pushes to the pull request's branch. Then it POSTs a GitHub-shaped `pull_request` / `synchronize` payload to the local server's webhook (`http://localhost:4317/api/github/webhook`, basic auth from `CS_BASIC` in `work/server.env`, never print it; that is how the review of the new head starts; GitHub itself cannot reach this box, say so in the README).
5. **Capture the author agent's session with Entire** (entire.com's open-source CLI: `curl -fsSL https://entire.com/install.sh | bash`, then in the scratch clone `entire enable` with the Claude Code integration; "works in any Git repository, no account needed"; read `entire --help` and https://docs.entire.com for where checkpoints are stored and how to read one for a commit). The session checkpoint is linked to the fix commit. Push the checkpoint data to our private sample repository only if that is how the CLI stores it (a branch such as `entire/checkpoints/v1`); do not sign in to anything, do not mirror the repository to Entire's hosting. Then make Countersign read it: in `intake` (or a small stage `provenance`), when the reviewed commits have Entire checkpoints, record `provenance: { tool: 'entire', commits: [{ sha, sessionId, agent, model?, prompt (the first instruction, truncated), toolCalls, testCommands: [{ cmd, lastOutcome }], files }] }`, and one deterministic cross-check: what the session shows the agent ran and saw, against what Countersign's own sandbox run found ("the author's session ends on a passing run of N tests; our run of the same tests on the same commit: N pass" or the mismatch). It is labelled as the author's own account: context for the human, never evidence, never a reason to skip a line. If the Entire CLI cannot be made to capture a headless `claude -p` session within 25 minutes, stop, write down exactly what happened in the README, and finish the loop without it.
6. **Run it once for real on #1**: post the fix request (through the pipeline's publish step on the existing dossier: if that needs a re-publish, run only the stage needed, e.g. `--fresh publish`, not a full review), run the author agent, let the webhook start the review of the new head (a full review takes about 8 to 12 minutes and several dollars of pool budget; at most 2 full runs), and check the result: the new dossier's `rounds`, `reproof` (did FN1's test go from fail to pass?), new findings, the reading plan now against before, the status and comments on the pull request (`curl -u ... localhost:4317/api/dossiers/<slug>/github`). Whatever happened is the result: if the agent's fix is wrong and the test still fails, or the fix introduces something new, that is what you report, and do not tune anything until it looks good. **Do not sign anything off or request changes in the product as a person, on any instance; do not answer decisions or judge findings.** That is for the human.
7. `work/author-agent/README.md`: what the loop is, the exact commands to re-run it, what happened on #1 with the commit shas and times, wall time and cost, and the honest limits (local webhook POST, one sample, the agent is ours).
