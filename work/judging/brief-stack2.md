# Task: a second stack for Countersign (Python / pytest), shown end to end on a new sample pull request

You work alone, overnight, no human to ask. Decide everything yourself. Do not start subagents. Hard stop: done and reported by **03:50 UTC** (check `date -u`). If you run short, a working red-to-green + regression + probe path with ablation and self-test honestly marked "not run on this stack" beats a half-working everything.

## Background

`/home/ubuntu/junction/linearcodereview` is "Countersign", a hackathon project (Junction 2026, challenge "Earned Trust in AI Code"): an AI review pipeline that turns a GitHub pull request into a dossier (`data/dossiers/<slug>/dossier.json`, type in `shared/dossier.ts`) and routes to a named human only the lines no executed check covers. Read `docs/CONCEPT.md`, then `pipeline/review.ts`, `pipeline/lib/{ctx,sandbox,policy,gh,agent}.ts`, `pipeline/stages/{intake,map,prove,probe,review,selftest,route,audit,publish}.ts`, `sandbox/*`, `policy/default.yml`, `policy/messagepack.countersign.yml`.

Today everything that executes code is wired to one stack: `policy.sandbox.adapter === 'dotnet'` (see `planTests`, `prove.ts`, `probe.ts`, the `canRun` checks in `review.ts` and `selftest.ts`, `sandbox/run-tests.sh`, `sandbox/trx_result.py`, `pipeline/lib/sandbox.ts`). Three hackathon judges named "one stack" as a reason the project loses on Practicality ("One second stack, even a toy one", "add adapters or an explicit supported-stack selection strategy"). This task removes that reason.

## What to build

1. **A sandbox adapter interface and a second adapter.** Pull the stack-specific parts behind one small interface (what a stack must provide: which test files/projects cover a source path, run a set of tests in the isolated sandbox at a given worktree and return per-test outcomes, how an independently written test is placed and run, which file extensions are source). Keep the dotnet behaviour byte-for-byte the same in effect (the five existing sample reviews must still work; run `bun test server/` and `bunx tsc --noEmit --skipLibCheck -p .` after your changes, and do not re-run the existing sample reviews). Add `adapter: "python"`: pytest inside a container with no network (same isolation rules as the dotnet runner: read `sandbox/run-tests.sh` to see what it guarantees and keep those guarantees), results from pytest's JUnit XML. Red-to-green (the PR's own tests fail on base, pass on head), regression (the base's tests still pass on head), ablation (revert one changed hunk, do the tests notice), independent probes (an agent that has not seen the PR's tests writes a test per acceptance criterion) and finding reproduction in `verify` must all work on the python adapter the same way they do on dotnet. The self-test (planted bugs) should work too; if you cannot get it working in time, make it skip with an honest "not checked" line.
2. **A new sample repository and pull request, all synthetic.** Create a **private** GitHub repository under the signed-in account (`gh repo create ToukoUrsin/junction26-countersign-python-sample --private`). Content: a small, realistic Python library written by you (about 400 to 800 lines of source plus a real pytest suite; something a consultancy would recognise, e.g. invoice totals with VAT and rounding rules, or a rate limiter; no real company names, no real data). Put the repo's Countersign policy file in it the way `loadPolicy` in `pipeline/lib/policy.ts` expects (areas, floors, `sandbox.adapter: python`, test map), so the policy is read from the base branch, not from the PR. Open an issue that states a requirement with testable acceptance criteria and one real ambiguity the text does not settle. Then open a pull request from a branch named like an agent branch (`agent/issue-<n>`), written as an AI coding agent would write it: it implements the issue with tests, references the issue (`Fixes #<n>`), touches 3 to 6 files and 80 to 250 changed lines, contains one mechanical part (a rename or a moved helper) and **one genuine subtle defect** the PR's own tests do not catch (e.g. a rounding edge, an off-by-one at a boundary, a silently changed default). Do not hint at the defect anywhere in the repo, PR or commit text.
3. **Protect the base branch** of the new repo so the status check `countersign/sign-off` is required (look at how the existing private sample repo `ToukoUrsin/junction26-messagepack-csharp` has it: `gh api repos/ToukoUrsin/junction26-messagepack-csharp/branches/main/protection`).
4. **Run the review end to end through the webhook**, the way GitHub would start it: the real server runs on `http://localhost:4317` (basic auth: user and password are in `work/server.env` as `CS_BASIC`; never print them). It must be restarted to load your pipeline changes only if server code imports changed; the pipeline is spawned as a fresh `bun pipeline/review.ts` process per review, so normally no restart is needed. POST a GitHub-shaped `pull_request` / `opened` payload to `/api/github/webhook` (see `server/index.ts`). The review then runs, posts its dossier comment and a pending `countersign/sign-off` status on your new pull request, and appears in the inbox. Check the dossier: stages done, criteria with executed proof, findings (did it find your planted defect? report honestly either way; do not tune the pipeline or the PR until it does), the reading plan, the comment and status on GitHub (`curl -u ... localhost:4317/api/dossiers/<slug>/github`). Fix real bugs in your adapter and re-run with `--fresh all` as needed (at most 3 full runs). **Do not sign anything off** in the product; the human does that.
5. Record the wall time and what happened in `work/stack2/README.md`: what the adapter interface is, what a third stack would need (in lines of code and the list of functions), what works and what does not on python, whether the planted defect was found and by which stage, and the exact commands to re-run.
